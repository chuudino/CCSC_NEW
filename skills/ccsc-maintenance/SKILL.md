# 小會網站維護

在既有 CCSC_NEW 工作目錄完成使用者要求的修改或審核。使用 [專案對照表](references/project-map.md) 找到內容、介面、標誌及部署設定；保留現有架構與使用者提供的素材。

## 接手與審核

1. 讀取專案 `AGENTS.md`、`README.md`、`CONTENT_NOTES.md` 與 `.openai/hosting.json`。
2. 重新取得 GitHub `origin/main`、Sites 來源分支及正式部署提交，核對本機工作樹、staged 差異與 HEAD；附件只作有版本的接手快照。分清未提交、未推送、來源已推送、已保存及已部署的狀態；無法讀取某個環境時，不宣稱其所有修改已同步。
3. 保留既有協作修改。若 Git 把相同檔案同時列為刪除和未追蹤，先檢查索引與分支同步副本，備份後再修復；這種狀態本身不是刪除網站檔案的授權。不要以重設工作樹消除未確認的修改。
4. 審核實際內容差異及引用資產。名稱或標誌改動須涵蓋頁首、頁尾、HTML 標題、description、favicon 和相關文章作者；照片或標誌保留實際尺寸比例與適當替代文字，並注意長名稱在手機頁首的空間。

## Worktree 並行開發與整合

開始並行任務、接手其他分支、執行 rebase、處理衝突或發布並行成果前，完整閱讀 [Worktree 協作流程](references/worktree-collaboration.md)，並遵守以下規則：

- 每項任務使用獨立分支與 `git worktree`；不要讓兩個工作者共用同一工作目錄或分支。先分配負責範圍、基準 SHA、依賴、驗證方式與唯一整合／發布者，再開始修改。
- 不同頁面可同時開發；`src/data/site.ts`、`src/App.tsx`、`src/styles.css`、依賴及部署設定等共用檔案，先劃分區段或指定單一負責者。Worktree 不會消除語意衝突。
- 合併前更新兩個遠端；由任務負責者將尚未共享的任務提交 rebase 到最新整合提交，逐一解決衝突並重新驗證。前一任務整合後，下一任務必須重新以新的整合 HEAD 為基準；不得一次平行 rebase 後直接合併全部任務。
- 由單一整合者依序 fast-forward 已更新的任務分支，並驗證組合成果。只改寫本人的未共享任務歷史；不得 rebase `main`、已發布或其他人正在使用的提交，不得強制推送。已共享分支需要改寫時，改建新分支或保留歷史合併。
- 發布只從整合工作樹執行。將同一完整提交同步到 GitHub 與 Sites 來源，再使用 Sites 保存及部署；任何遠端前進、推送拒絕或發布者衝突，都先保留成果、重新整合及驗證，不把部分同步當成完成。

## 內容與品牌

- 全名為「天主教中華基督神修小會」，簡稱「小會」；英文名稱為 `Chinese Christian Spirit Community`。共同成長的既有用語是「偕行」。
- 史料、引用、外站名稱及來源原文不隨品牌文字做全面取代。快照疑點維持 `CONTENT_NOTES.md` 的待審狀態，除非使用者或可信來源提供更正依據。
- `public/ccsc-mark.svg` 是依既有標誌重繪的透明向量原檔，供 `SacredMark` 與 favicon 共用；`public/ccsc-mark.png` 保留為原始參照。更新時保留既有輪廓及紅、深藍、金色，維持 SVG 的 viewBox 比例，不在圖檔內加入不透明底色。首頁的半透明霧面效果由 `.hero-art__mark` 的 CSS 處理；頁首、頁尾標誌保持去背。

## 驗證與同步

- 依變更選擇檢查；`npm run build` 包含 TypeScript 檢查及 Vite 正式建置。需要單獨檢查型別時使用 `npm run typecheck`。依賴未變且已可用時不重裝；需要重建依賴時沿用 `package-lock.json`。
- 執行 `git diff --check`，查看待提交檔案，確認 `.env`、憑證、備份、`node_modules/`、`dist/` 和預覽暫存資料未納入提交。
- 若修改本技能，執行 skill-creator 的 `quick_validate.py`，核對參考連結與 `agents/openai.yaml`，並同步使用者已安裝的本技能副本。技能的版本來源是專案內 `skills/ccsc-maintenance/`；本機 Skills 副本須依目前 skill-creator 流程提交及推送，不能只複製檔案就宣稱已儲存。涉及 Git 流程時以隔離測試儲存庫演練，不在正式遠端製造測試提交。
- 建置後用 `npm run verify:build` 檢查正式標題、description、標誌、favicon 與 HTML 資產引用。瀏覽器檢查依目前 Sites 技能與環境能力執行，清楚記錄無法完成的驗證。

## Sites 正式發布

使用已安裝的 Sites 技能和原生工具處理來源、封裝、保存版本與部署，不將過期工具參數寫成固定流程。保留 manifest 的 `project_id` 與網站當前受眾，不建立替代網站。

Sites 是正式部署管道；GitHub 用來保存完整程式碼、內容、技能與維護紀錄。不要為了發布另設 GitHub Pages、CI 或 Actions；只有使用者另有要求時才新增這些流程。

- 先取得現有 Site 與短期來源憑證，透過 Sites 的來源 helper 開啟並核對來源後編輯；憑證只保留在執行記憶體，經 stdin 傳入 helper。
- 依 Worktree 協作流程完成串行整合，確認沒有未完成的 merge／rebase、未提交修改或其他已知發布者，再記錄準備發布的完整 SHA。GitHub `origin` 與 Sites 來源是兩個同步目的地；兩者都須包含已確認的協作成果，不以較舊的 Sites 快照覆蓋 GitHub 技能。
- 發布前再次核對兩個來源分支與 Sites 最新保存／部署狀態，將審核後相同的完整 SHA 推送到兩者。若任何遠端前進或拒絕推送，停止保存／部署、保留已成功推送的提交，依參考流程重新整合；不得 rebase 已推送的發布提交或強制覆寫遠端。
- 使用 Sites helper 的來源結果與已驗證輸出封裝；成功檢查且輸入未變的步驟不重跑。保存版本時使用 helper 回傳的完整 SHA 和 archive。
- 保存及部署前各再次核對版本與發布狀態，確認仍是預定提交，避免較舊任務晚完成而蓋過新版本；部署已保存且對應該提交的版本。只對非終態部署繼續查狀態；成功後回報正式網址、版本號、GitHub 提交、驗證結果及剩餘內容待辦。
- 檢查最終工作樹與兩個來源提交的一致性。只有部署成功才能說網站已更新；只有推送成功才能說 GitHub 已同步。

## 雙端版本一致的完成條件

- 每次發布都將同一個完整提交推送到 GitHub `main` 與現有 Sites 的來源分支；包含本次修改的技能與文件，不只比對網站畫面或 `src/`。
- 發布前重新讀取兩端最新提交。先整合新增或分歧的歷史並重新驗證，禁止強制推送、重設遠端或用較舊來源覆蓋協作者的修改。
- 確認 GitHub `main`、Sites 來源分支、Sites 已保存版本的 `source.commit_sha`，以及成功正式部署所屬版本，全部對應相同完整 SHA，才回報「版本已一致、同步與發布完成」。記錄 SHA、版本號、部署結果與正式網址。
- 任一端推送、保存或部署失敗時，保留已完成的提交，分別回報成功與未完成的目的地；不要把「已推送 GitHub」「已保存版本」或「內容看起來相同」當成整體完成，也不要以空提交掩蓋差異。
- 官網內容同步與程式版本同步分別記錄。公開來源受阻、日期不明或刊物暫緩時，只採用可核實的資料，列出待辦；不把無法讀取算成內容不存在，也不因此宣稱已完整對齊官網。
